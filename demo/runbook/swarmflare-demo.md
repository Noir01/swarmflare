# Swarmflare supported demo walkthrough

This is a bounded demonstration of the collaboration platform, not a production Git host. The separate project-list application inside the sample candidate is the work being reviewed, not Swarmflare itself. The current sample was prepared first-party source; independent review was actually performed by Luna. Do not describe it as a fresh swarm implementation campaign.

## Before presenting

An authorized operator checks the exact development deployment, then performs only an attended, bounded ingress renewal if required. DEMO_EXPIRES_AT is an integer millisecond deadline; previews expire after about 110 seconds and runner sessions after 120 seconds. No perpetual refresh loop is used. Run the explicit native helper sequence only against the existing generated synthetic fixture. Do not read its credentials into transcripts, screenshots or a recording.

The current signed source, verification commands and limits are in README.md. Preserve the existing baseline, source refs and failed evidence. Public browsing does not require login. Owner setup/acceptance is a separate, deliberately unrecorded credential boundary; do not show passwords, cookies, CSRF values, grants, runner-service keys or cloud configuration on screen.

## A five-to-eight-minute presentation

1. Landing and How it works (about one minute)

Explain the product: repository source, a shared task, scoped contributors and reviewers, evidence, and a separate owner decision. The landing example is labeled illustrative. Open the first-party agent guide from the tutorial. It is instructions, not credentials or an automatic agent launcher.

2. Repository source and ownership (about one minute)

Open the sample repository from the actual public catalog. Inspect Code and README from actual Artifacts source. Explain signup/login and ownership as implemented features without logging in as a real user during automation. Creation can initialize a README; public import is restricted to octocat/Hello-World on master. Imported code is never executed by this demo. Do not claim arbitrary provider/private repository support.

3. Task and preserved failure history (about one minute)

Open Tasks and Candidates. Task proposal, owner approval, policy and verified baseline initialization are distinct. Explain the supported six obligations and two mandatory checks. Earlier candidate records retain failed reviews: a late tenant response race and missing Previous navigation, followed by unsigned cursor tampering. Passing initial mandatory checks did not override independent findings.

4. Current candidate (about two minutes)

Open the checked signed-cursor replacement. Conversation shows the approved task, review context and resolved findings; the sidebar says ready for human review, not accepted. Files changed shows the exact baseline-to-candidate patch. Checks shows actual API/UI execution evidence; raw receipts and hashes remain in details. The replacement's actual independent Luna verdict is recorded under a separate reviewer actor, and each finding resolution cites applicable checks and review evidence.

5. Supported preview (about one minute)

Refresh the preview only through an authorized short-lived operator session immediately before showing it. Open Preview, then Next, Previous and tenant B. Explain the yellow scope banner: actual bounded API responses were recorded through one sandboxed handler and are replayed offline; other requests are refused. This is not arbitrary deployment or live application hosting. Expiry is a deliberate safety boundary, not evidence loss.

6. Human decision boundary (about one minute)

Readiness is not acceptance. Only the authenticated repository owner can review the fresh pinned snapshot, tick the review checkbox, confirm, then perform a separate acceptance action. Stale or changed evidence is refused. Do not take these actions for the owner, and do not depict acceptance or a baseline change that did not occur.
